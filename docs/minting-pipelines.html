Two minting pipelines that never meet

Project minting builds the containers. Task minting fills a project slot on every task it creates. In 1,123 measured candidates, that slot was filled zero times.

The two lanes run on different clocks and different units — one per company on demand, one per file during enrichment. Nothing schedules them together.

02Project minting, stage 1: what puts a file in a cluster

A cluster is every file that belongs to one outside company. Three signals put a file there, and a file can arrive by more than one.

connectors/project-minting.ts:306 · clusterClientFiles

SignalFile membershipsRule
participant_domain1,944Someone on the file has an email at the company's corporate domain.
dedicated_channel309The file came from a channel named after the company.
family_accretion198The file shares a recurring title family with files already in the cluster.

Companies are deduplicated first, so shards join as one cluster — Oliver Wyman and OW are two entities and one cluster. Own-org groups and email-provider names (Gmail, iCloud) are dropped before any of this runs.

Channel matching requires the complete name. A company called "Sketch Design" cannot claim the #design channel from a fragment of its own name. That rule exists because the earlier substring version over-linked heavily.

03Stage 2: the trigger, and why most clusters stop here

Existing is not the same as worth asking about. A cluster is only sent to the model if it shows a rhythm.

export function clusterIsTriggered(families: TitleFamily[]): boolean {
  return families.some((family) => family.count >= 2 && family.distinctDays >= 2);
}

One title family — a normalised subject or meeting name — has to appear at least twice, on at least two different days. One long thread on one day is not a relationship.

The filter does its work at the small end. Every cluster with 10 or more files triggers; below 5 files, most do not. The largest are Oliver Wyman (689 files, 2 shards), Getepik (409, 2 shards) and Habuild (336).

04Stages 3–5: the model nominates, a human declares

The dossier is built by code, not by a model — files, people, channels, tracker containers, and what the registry already says about this counterparty. The model reads it and returns a verdict.

What the model returns is a nomination, never a declaration. It proposes two axes — what the counterparty is (client, vendor, investor, partner, other) and, for a client or partner, where the relationship stands (prospect, pilot, active, dormant, ended). Accepting is what turns the reviewer's answer into the declaration.

connectors/project-minting-acceptance.ts:200 · acceptedProjectsForConfirmedAxes

The stage decides the shape that may be written:

ConfirmedContainerProjects
vendor · investor · othernonenone
dormant · endednonenone — existing entities untouched
prospectmust be absentpermitted
pilota project, not an engagementat least one
activean engagement, requiredas proposed

Two rules resolve every case: the gate never invents shape, so a confirmed stage needing a container the verdict lacks is refused; and it never mints above the confirmed ceiling, so correcting downward drops the excess and reports what it dropped.

I got the pilot row wrong first time. I wrote a build brief saying "pilot and active get a container", which reads as an engagement for both. The prompt actually mints a pilot's container as a project named "<Counterparty> deployment" with a null engagement. A gate built from my sentence would have refused every correctly-formed pilot verdict. A review caught it before it was built.

05Task minting: a different unit, a different clock

Task minting runs per file, inside enrichment. It does not know about clusters, and clustering does not know about it.

connectors/task-minting.ts:114 · mintTasksFromFile

The first step decides everything downstream: the 20 nearest files by embedding distance. That neighbourhood is what "relevant open tasks" and "relevant projects" are computed from. A file with no embedding gets no neighbourhood, and its context collapses to itself.

Then five context blocks go into the prompt:

BlockCapSelected by
Attendees—People on this file.
Projects100Live and visible; those mentioned in the 20 nearest files first, then A–Z.
Open tasks60Evidenced in the 20 nearest files, plus tasks assigned to this file's attendees.
Prior titles50Titles already minted, so the model can avoid repeating itself.
Parent refs—Tracker containers this file already belongs to.
Minting reads globally on purpose. The neighbourhood query applies no visibility filter. The comment in the code is the design: the control that matters is on what minting writes, not what it reads.

06The gate: an honesty flag, or a second file

The model returns hasOwnerVerbObject — its own claim that the text named a person, an action, and a thing. That flag is the whole gate.

entities/materialize-llm-task.ts:7 · materializeLlmTask

const corroborationCount = await countCorroboratingFiles(deps, raw.corroborationKey, ownerUserId);
if (raw.hasOwnerVerbObject || corroborationCount >= deps.llmTaskCorroborationThreshold) {
  // …write the task
}
return { kind: "skipped", reason: "llm_task_ungated" };

A confident candidate is written from one file. An unconfident one waits until the same normalised title shows up in a second file (LLM_TASK_CORROBORATION_THRESHOLD, default 2). Before either check, collation runs: if a task with that title and parent already exists, the candidate becomes extra evidence on it rather than a new row.

A gated candidate is stamped materialized_at anyway. All 1,123 facts carry a materialization timestamp, including the 232 that produced nothing. The flag means "processed, do not retry", not "became a task" — shouldMarkMaterialized returns true for skipped unless the reason is one of five specific ones, and llm_task_ungated is not among them. Querying materialized_at to find what minting produced gives 100% and is wrong.

07Where the two pipelines were supposed to meet

The wiring exists. Task minting sends up to 100 projects into the prompt, each with a short id. The model may return a projectId, which is resolved through a lookup table — an id, not a name match, so it cannot invent one.

const project = typeof record.projectId === "string" ? projectsById.get(record.projectId) : undefined;
return [{
  title: record.title.trim(),
  /* … */
  ...(project ? { parentEntityId: project.id, projectName: project.name } : {}),   // never taken
}];

Measured across every stored candidate:

MeasureCountOf
Candidates naming a project01,123

All 1,123 facts carry promptVersion: "llm-task-v1", which is the version the code runs today, minted 6–13 July 2026. So this is not a stale-snapshot artefact of an older prompt. It is what the current prompt produces on this corpus.

This is the finding. Project minting's entire output is a set of containers. Task minting has a slot for exactly that, sends the candidates, and fills it zero times out of 1,123. Every model-minted task in this workspace is parentless.

What I did not measure, and would need before assigning a cause: whether the projects block was non-empty in those runs. The block is assembled at mint time and not stored on the fact, so a run against a workspace with few projects is indistinguishable from a model ignoring a full list. The 78 live projects exist now; how many existed in early July, and how many survived the visibility filter and the 100 cap, is not recoverable from the stored data. That is the next thing to measure, and it decides whether this is a prompt problem or a context problem.

09Where this stands

  • Project minting works through stage 5 and now has a review surface at /dev-tools. Nothing triggers it over HTTP — the pass runs from scripts/project-mint-pass.ts.
  • Task minting runs automatically inside enrichment and needs no operator.
  • The two do not compose. The link is one field, it is wired end to end, and it has never carried a value.
  • Open, and decidable with one measurement: whether the projects context block is arriving empty. Until that is known, do not change the prompt.
